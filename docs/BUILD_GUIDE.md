# Building Account Register with Bare React Native

## 1. Purpose and current boundary

This project is an offline-first digital account register and filing system. It is designed to organize accounts, services, platforms, subscriptions, projects, clients, and generic user-named links. Social-media accounts are one category among many. It is not intended to replace a password manager.

The app persists ordinary records locally through a small manually registered Android bridge. Passwords are kept outside ordinary register JSON and use the native secure-storage bridge when available. Sharing and export are intentionally deferred.

The implementation is organized around decoupled entities, route-based navigation, reusable generic-link editing, search/filtering, local security, and independently managed account, platform, project, category, and client records.

## 2. Why bare React Native

React Native is a JavaScript and TypeScript framework that renders native mobile controls. **Bare React Native** means that the repository contains the Android project directly. The `android` directory includes Gradle files, a Kotlin activity, an Android manifest, resources, and the application module. There is no Expo framework in this repository.

This choice is appropriate for this project because the intended output is an Android APK built by GitHub Actions, and you want to learn the native boundary rather than hide it. The trade-off is that Android SDK, Java, Gradle, and native dependency problems become your responsibility. The project therefore starts with very few libraries.

## 3. Compatibility baseline

The scaffold was generated with React Native `0.86.3`. React Native `0.86` is a practical pin for this project because it has a current Android template and does not force us to follow a moving `latest` tag. The official React Native release notes describe the next `0.87` line as requiring Node 22, Android Gradle Plugin 9, and Kotlin 2.0 or newer. This project remains on `0.86.3` so its dependency graph can be kept stable while you learn.

| Component | Project choice | Reason |
| --- | --- | --- |
| Node.js | `22.13.0` | Fixed in `.nvmrc`; compatible with the project engine declaration |
| React Native | `0.86.3` | Pinned template rather than an unbounded latest version |
| React | `19.2.3` | Installed by the React Native template |
| React Native CLI | `20.1.0` | Installed by the template and kept aligned with the RN line |
| TypeScript | `^5.8.3` | Type checking without introducing a separate build system |
| Android min SDK | `24` | Covers modern Android devices while keeping the template simple |
| Android compile/target SDK | `36` | Generated by the current template |
| Gradle wrapper | `9.3.1` | Generated wrapper; CI uses the wrapper instead of a machine Gradle install |
| Kotlin | `2.1.20` | Generated Android template value |
| Java in CI | JDK 17 | React Native documentation recommends JDK 17 and warns about higher versions |
| Navigation | None yet | One main screen does not need a navigation library |
| Storage | Android `SharedPreferences` through a manual bridge | Keeps the dependency graph small and avoids auto-linking |
| UI kit | None yet | React Native core controls are enough for the first screen |

The important rule is to change one layer at a time. Do not simultaneously upgrade React Native, the Android Gradle Plugin, Kotlin, and several native libraries. If you need to upgrade, create a separate branch, record the old and new versions, and build the empty app before adding feature changes.

## 4. What the generated folders mean

The repository is a normal JavaScript project plus an Android project.

| Path | Meaning |
| --- | --- |
| `App.tsx` | The main React component for this starter |
| `index.js` | The native entry point that registers the root React component |
| `package.json` | JavaScript dependencies and commands |
| `tsconfig.json` | TypeScript rules |
| `babel.config.js` | Converts modern JavaScript and TypeScript for Metro |
| `metro.config.js` | Metro is the React Native JavaScript bundler |
| `android/` | The native Android application and Gradle build |
| `android/app/` | The Android application module that becomes the APK |
| `android/app/src/main/AndroidManifest.xml` | Android app declaration and permissions |
| `android/app/src/main/java/.../MainActivity.kt` | Android activity that hosts React Native |
| `android/app/src/main/java/.../MainApplication.kt` | Android application setup and package loading |
| `android/app/src/main/java/.../AccountStorageModule.kt` | Native bridge that reads and writes non-secret JSON |
| `android/app/src/main/java/.../AccountStoragePackage.kt` | Manual package registration for that bridge |
| `android/gradlew` | Project-local Gradle command used by CI |
| `__tests__/` | Jest tests |
| `.github/workflows/` | Automated checks and APK build instructions |

The Android project is not a separate app from `App.tsx`. The Kotlin activity starts the native host, and that host loads the JavaScript bundle. You can think of it as a thin Android shell around the React Native interface.

## 5. How to read `App.tsx`

The screen is intentionally written as one file so you can trace the complete workflow.

`AccountRecord` is a TypeScript type. It describes the shape of one register entry. TypeScript does not run on the phone. Babel removes the type annotations during bundling and the TypeScript compiler checks them before that.

`sampleRecord` is sample data. `emptyDraft` is the blank form used when creating a new record.

`useState` stores changing values. The `records` state holds the current list. The `query` state holds the search text. The `showForm` state controls whether the form is visible. The `draft` state holds the values currently being typed.

`useMemo` calculates the filtered list. It reruns when either the search query or the records change. The search is deliberately simple: it joins the fields that should be searchable and checks whether the query is contained in that combined text.

`Field` is a small reusable component. It receives a label and all normal React Native `TextInput` properties. This is the first useful React pattern in the project: use a component when a group of markup and behavior repeats.

The main return value uses a `SafeAreaView`, a header, and either the form or the register list. `Pressable` creates buttons. `FlatList` renders a list efficiently and is the normal React Native equivalent of rendering a long list with a web loop.

The form validates three required values: client, platform, and account name. It then appends a new record to state. The archive action changes the status instead of deleting the record. This is a reversible first design and avoids premature destructive behavior.

## 6. Why the starter has no navigation package

A navigation library is useful when there are multiple screens. This version has one main screen and a form that can be opened from that screen. Adding navigation now would introduce another dependency and another set of concepts before they are needed.

When the project grows, use React Navigation rather than inventing a URL-like system. A likely future version would contain a register screen, a record detail screen, a client screen, and a settings screen. Add navigation when the screens are real, not as a placeholder.

## 7. Persistence implementation

The app uses Android `SharedPreferences` through a two-file native module. `AccountStorageModule.kt` exposes `load()` and `save(value)` to JavaScript. `AccountStoragePackage.kt` makes the module available, and `MainApplication.kt` adds the package manually. This is deliberately not an npm dependency, so there is no auto-linking configuration to debug.

A storage adapter keeps the rest of the app independent from the chosen library:

```ts
export interface AccountStore {
  load(): Promise<AccountRecord[]>;
  save(records: AccountRecord[]): Promise<void>;
}
```

The screen loads records inside `useEffect` when it starts and saves after adding or archiving. The Android preference name is `agp_preferences` and the data key is `records_json_v1`. The value is a JSON array of non-secret records.

Future tests should cover these cases:

1. A new installation loads an empty or sample-safe state.
2. A saved record comes back after a reload.
3. Invalid JSON does not crash the screen.
4. A record with missing required fields is rejected.
5. Archived records remain available but can be hidden by a filter.

If passwords are ever added, do not place them in ordinary preferences. Use a purpose-built secure storage design and write tests for lock behavior, backup behavior, clipboard clearing, and background screenshots. Until then, the password field is discarded by `addRecord`.

## 8. Suggested future data model

Keep the first persisted version flat. A flat record is easier to migrate than several related tables when the application is still being discovered.

```ts
type AccountRecord = {
  id: string;
  client: string;
  project: string;
  platform: string;
  accountName: string;
  email: string;
  username: string;
  password: string;
  status: 'Active' | 'Paused' | 'Archived';
  notes: string;
  createdAt?: string;
  updatedAt?: string;
};
```

Later, you can normalize clients, projects, and platforms into separate collections. Normalization means storing a client once and referring to it by an ID. It becomes useful when editing a client name should update many account records. Do not add that complexity until duplicate client data becomes a real problem.

## 9. Android and Gradle in plain language

Gradle is the build system used by Android. The wrapper file in `android/gradle/wrapper` tells the project which Gradle distribution to download. Always use `./gradlew` from the `android` directory or the wrapper invoked by the React Native CLI. This prevents the build from depending on whichever Gradle version happens to be installed on a computer.

The root `android/build.gradle` defines versions shared by Android modules. The `android/app/build.gradle` defines the application module, including its application ID, SDK levels, signing configuration, and React Native Gradle plugin.

The React Native Gradle plugin bundles the JavaScript for non-debug builds. A debug build normally connects to Metro on your development computer. A release build includes a bundled JavaScript file, so GitHub Actions can produce an installable APK without your laptop running Metro.

The workflow generates `android/gradle/wrapper/gradle-wrapper.jar` and `android/app/debug.keystore` after checkout. The generated debug keystore is for personal testing and is not a release signing key. If you later publish the application, create and protect a real release keystore outside the repository. Do not commit private signing keys.

## 10. Local commands

Run these from the project root:

```bash
npm install
npm run start
```

In another terminal, start an emulator or connect a device and run:

```bash
npm run android
```

Run the checks without a device:

```bash
npm run lint
npm test -- --runInBand
npx tsc --noEmit
```

If Android reports that no SDK is found, set `ANDROID_HOME` to the Android SDK directory and add its `platform-tools` directory to `PATH`. React Native’s official environment guide explains this setup in detail.

## 11. GitHub Actions build

The workflow in `.github/workflows/android.yml` uses Ubuntu, Node 22, JDK 17, and Android SDK 36. It installs Gradle 9.3.1, runs `gradle wrapper` to generate the wrapper JAR, creates a debug keystore when one is absent, installs npm dependencies with `npm ci`, runs linting, runs Jest, checks TypeScript, and assembles the release APK.

The APK is uploaded as a workflow artifact. It is not automatically published to Google Play. Open the completed GitHub Actions run, open the artifact named `agp-release-apk`, and download the ZIP containing the APK.

The workflow does not need Expo, EAS, a server, or a signing secret for the current personal testing project. The release APK is signed with the generated debug key because the app is not being published. This is not a store distribution strategy.

## 12. A practical feature order

Build features in this order:

| Step | Feature | Why it comes here |
| --- | --- | --- |
| 1 | Edit and detail view | Corrects mistakes and shows the complete record |
| 2 | Export and import | Protects against device loss without adding a server |
| 3 | Status and filters | Keeps the daily list manageable |
| 4 | Clients and projects screens | Removes repeated names when the register grows |
| 5 | Encrypted backup and restore | Protects against device loss without adding a server |
| 6 | App lock | Adds privacy after the data lifecycle is understood |
| 7 | Secure password storage | Only if the product genuinely needs it |

Do not start with cloud sync. Cloud sync changes the project from a local app into a distributed system, which adds authentication, conflict handling, backups, and a server. None of that is needed for the first personal tool.

## 13. Troubleshooting method

When a build fails, identify which layer failed before changing versions.

| Symptom | Likely layer | First action |
| --- | --- | --- |
| `npm install` fails | Node or package registry | Check Node version and network |
| TypeScript errors | JavaScript/TypeScript | Run `npx tsc --noEmit` and read the first error |
| Metro cannot resolve a module | JavaScript dependencies | Run `npm install`, then restart Metro with its cache cleared |
| Gradle cannot find Java | Java environment | Use JDK 17 and check `JAVA_HOME` |
| Gradle cannot find SDK | Android environment | Check `ANDROID_HOME` and installed SDK Platform 36 |
| Kotlin or AGP incompatibility | Native version matrix | Restore the pinned versions before making a targeted change |
| APK builds but does not install | Android device/signing | Check device API level, package ID, and APK architecture |

Avoid deleting `node_modules`, Gradle caches, or lockfiles as a first reaction. Start by reading the first meaningful error, because later errors are often consequences.
